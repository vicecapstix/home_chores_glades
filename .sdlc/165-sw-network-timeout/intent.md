## Problem
`src/public/sw.js` is network-first with no timeout: `fetch(req).catch(() => caches.match(...))`. On a weak connection (the tablet in the garden, a TV on 2.4 GHz), the fetch doesn't fail; it just hangs, so the app shell stays blank for 30–60 s even though a cached copy exists.

## Outcome / acceptance criteria
- [ ] Navigation and same-origin GET requests race the network against a timeout (e.g. 3 s); on timeout the cached response is served if there is one, and the network response still refreshes the cache when it arrives
- [ ] With no cached copy, behaviour is unchanged (wait for the network)
- [ ] Cache name bumped so clients pick up the new worker
- [ ] Firebase/auth/font requests stay untouched (cross-origin)
- [ ] Tests: SW logic extracted into a testable function (or tested with mocked `fetch`/`caches`): slow network → cache, fast network → network, offline → cache

## Affected users
Everyone on phones, tablets and the TV.

## Constraints
- Cost guardrails: stays on GitHub Pages (`main` / root) and the existing Firebase RTDB on the free Spark plan. Never write to or change rules on the live DB; tests use mocks only.
- Same-origin caching only; no new storage beyond the existing Cache API shell.
- Deploy: run `npm run build:pages` and commit the root files so merging deploys (CI fails on drift).
